## 1. What the owner asked for

Verbatim in substance: a commander and outpost must be able to **survive a regional or cluster outage**. The commander, outposts, and retrans must have the ability to **span multiple regions and clusters**.

## 2. Vocabulary first: an instance's own geography is not "region"

`region` is reserved vocabulary: *a geographic locality within a security domain* — a property of the **tenant's** deployment targets (`amer`/`apac`/`emea`), load-bearing for stage-name derivation and the M15.6 regional-deploy gate ([GLOSSARY.md](../GLOSSARY.md) "region", "deployment target"; [ADR-0026](../adr/0026-placements-and-derived-stage-names.md) D1). It describes where the *coordinated workloads* run, never where SCP itself runs. This proposal therefore needs distinct terms for SCP's own placement:

- **Instance** — one running deployment of the SCP platform around **one PostgreSQL database**. An instance is **multi-tenant**: it hosts N orgs, and federation identity, journal, cursor set, peer set, *and federation role* are all **per-org** (`federation_self` is keyed by `orgId` with a per-org `role` column, [schema.ts:1256](../../apps/server/src/db/schema.ts); the journal chain is per `(org, originDomainId)`; DESIGN.md §13 explicitly leaves per-deployment identity **open**). So "a commander" is, precisely, *an instance at least one of whose tenant orgs holds the commander role*. **The database is the unit that must survive an outage**; everything per-org rides inside it. This proposal amends the GLOSSARY `instance` entry (D1): the definition gains "whose api/worker compute may span several member clusters" — one Postgres stays load-bearing.
- **Member cluster** — one Kubernetes cluster (or compose/VM site) running some of an instance's api/worker compute. An instance *spans* one or more member clusters. New term (D1).
- Where geography must be named, the prose says **infrastructure region**, always qualified — never bare "region".

The core stance in one sentence: **multi-cluster is a property of an instance, not a multiplication of instances.** An instance spanning three clusters in two infrastructure regions is still one database and one per-org journal set. The alternative — a second "standby" instance with its own database — is rejected in §10. A consequence of multi-tenancy worth stating: a multi-tenant commander's failover moves the dial address for *every* tenant org's peers at once, and mixing commander-role and outpost-role tenants on one database couples their DR postures (§11 D2).

## 3. What already exists (grounded — the architecture is closer than it looks)

The event/reconciliation architecture already concentrates **all correctness in Postgres** with **N competing, crash-resumable workers** (DESIGN.md §8: "any worker can resume after a crash because no state lives in memory"). Measured against the code, most of that promise is real:

- **Change coordination is proven multi-replica-safe.** Per-change session-scoped advisory locks ([change-coordination-lock.ts](../../apps/server/src/coordination/change-coordination-lock.ts)), `FOR UPDATE SKIP LOCKED` claims for outbox relay and webhook/observed events ([outbox-relay.ts:113](../../apps/server/src/events/outbox-relay.ts), [webhook-processor.ts:396](../../apps/server/src/coordination/webhook-processor.ts)), and real N-concurrent `Promise.all` integration races for trigger claim, plan compile, gate evaluation, and event processing ([coordination.integration.test.ts:1083–1605](../../apps/server/src/coordination/coordination.integration.test.ts)). The chart already ships api×2 + worker×2 as the default. One honesty qualifier: this guarantee is **per-entity, not architectural** — *campaign* coordination had the identical shape with no lock and no race test until A2's fix (§4) was absorbed into M25, so a safety claim here is exactly as wide as the tests behind it.
- **LISTEN/NOTIFY is latency-only.** The 1-second poll is the documented correctness fallback ([outbox-relay.ts:27](../../apps/server/src/events/outbox-relay.ts)). Nothing correctness-bearing rides a broker.
- **Every federation connection is outpost-initiated** (DESIGN.md §13, ADR-0009). Only the commander's *dial-in address* has to survive a failover; no commander→outpost connectivity needs re-establishing (poke is best-effort and backstopped by the pull cadence).
- **Outposts already tolerate commander outages by construction.** Reconcile candidates filter on `originDomainId = federation_self.domainId` ([changes-repo.ts:694](../../apps/server/src/coordination/changes-repo.ts)), so an outpost keeps coordinating its own changes while commander-origin replicas merely go stale — and freshness reporting is honest about it (upstream-freshness anchoring, DESIGN.md §13).
- **Signing identity rides the database.** Per-org federation Ed25519 keys (`instance_keys`) and cosign keys (`instance_cosign_keys`) are Postgres rows ([schema.ts:1088](../../apps/server/src/db/schema.ts), [cosign-keys.ts](../../apps/server/src/governance/cosign-keys.ts)) — a promoted standby has them with no separate migration.
- **Retrans is already crash-safe and replica-safe within one instance.** Lease-fenced atomic claims (`claimRelayBuild`, [relay-builds-repo.ts:128](../../apps/server/src/federation/relay-builds-repo.ts)), scratch-dir builds, atomic-rename publication, Postgres written only after the whole pipeline succeeds ([retrans-relay.ts:538–802](../../apps/server/src/federation/retrans-relay.ts)). §9.4 qualifies what "retry" covers.
- **pg-boss lives in the same database** (schema `pgboss`, [pgboss.ts:126](../../apps/server/src/events/pgboss.ts)) — a failover moves job state and application state in lockstep. (§7.4 explains why a *restore* makes this lockstep a hazard, not only a convenience.)

What does **not** exist: any statement of how an instance survives losing the cluster it runs in. DESIGN.md §17's Availability row reads, in full, "HA via the org's standard Postgres HA"; the charter's Availability NFR reads "Enterprise-ready"; no milestone touches DR; and there is **no backup/PITR/restore tooling or documentation** — a gap [ADR-0024](../adr/0024-decision-and-audit-retention.md) F9 already names (a growth/sizing/backup runbook under `docs/runbooks/`, priority "now", never built). §7.4 subsumes F9.

## 5. The design: one instance, many member clusters

Four invariants, then the mechanics.

**I1 — One writable primary, guaranteed below us — and the consequence stated.** At any moment exactly one Postgres primary accepts writes for an instance. SCP does not build or ship this guarantee: it is the operator's Postgres HA layer (streaming replication + Patroni, CloudNativePG, a cloud-managed service — all fine, all air-gap-compatible in their self-hosted forms). SCP **states the requirement precisely** (ops runbook, §8), including its teeth: **if fencing fails and a demoted primary keeps taking writes, SCP detects nothing and silently loses those writes** — every serialization primitive SCP uses (advisory locks, sequence uniqueness) is per-database and satisfied independently by both sides of a split brain. That residual risk is either accepted in writing (§10) or narrowed by the promotion-runbook generation stamp (§7.2.6). SCP adds **no second consensus store** (charter principle 4 — this proposal needs no new required stateful dependency, and that is a feature, not an accident).

**I2 — Compute is symmetric and stateless across member clusters — and all of it reads the primary.** One Helm release per member cluster, all pointed at the same logical DSN, all sharing the same `appSecrets`, `postgres.existingSecret`, and mTLS material (§6). There is deliberately **no read-replica offloading of correctness reads anywhere in this design**, and the reason is concrete, not conservative: read-time admission predicates — policy gates, freeze holds (including M25's per-target freeze admission, re-evaluated every tick by whichever worker claims the change) — are correctness reads, and an instance that offloaded them to a replica would evaluate a freeze against lagged state and **silently ship into it**. So every worker reads and writes the one primary. Once Class A is fixed, the competing-consumer design makes any worker anywhere correct; workers far from the primary run with degraded tick latency (the reconcile hot path is per-row round trips), which degrades staleness, never correctness. Guidance, not machinery: run the bulk of worker capacity near the primary; a distant member cluster is a survival organ, not a latency optimization.

**I3 — One dial address per instance, with a fallback list.** The primary answer to "outposts must reach whichever cluster is alive" is operator DNS/VIP/GSLB on the commander's base URL — zero schema change. But air-gapped and enclave networks routinely lack failover DNS, so the peer row additionally grows an **ordered list of dial URLs** (D3): tried in order per pull attempt, each attempt under an explicit per-URL `timeoutMs` (the poke path's precedent — the pull path today has none, B6). Constraints found in review, now part of the design: `requireMtls` is derived from the URL scheme ([federation-outbound.ts:100](../../apps/server/src/federation/federation-outbound.ts)), so the list **refuses scheme downgrades at write time** (an `https` base with an `http` fallback is a 400, not a silent bearer-only dial); and the commander's federation server certificate must carry **every** dial name (VIP, GSLB name, each fallback host) as a SAN — a runbook precondition (§8). Honestly stated: the list is provisioned per outpost through the same door as B6's PATCH (ADR-0022: peer rows are local, per-side, never journaled); its value is that it is provisioned **before** the failover instead of during it.

**I4 — RPO > 0 must be loud.** Synchronous-quorum replication (RPO=0) is the *supported* posture for a commander-hosting instance (D2, settled) and the only posture in which B1/B2 cannot occur. But async replication is a legitimate operator choice for outposts and retrans, so the platform must convert "lost tail" from silent divergence into a named, fail-closed, Decision-recorded event (§7.2). We defend the failure model we cannot forbid. **D2's owner condition, recorded here because it is an invariant, not a preference:** this posture governs *database replication only* — it neither enforces poke mode nor alters federation transport in any way. Outposts and retrans work in isolation, and when connected (non-air-gapped) they regularly poll the commander on their own cadence; poke stays strictly opt-in (ADR-0009).

### What each role needs beyond the common pattern

- **Commander-hosting instance** — the full pattern. Sync-quorum recommended (D2); divergence rails mandatory. Note the multi-tenant coupling from §2: the posture is per *instance*, so it is set by the strictest role any tenant holds.
- **Outpost-hosting instance** — the same pattern at whatever tier the domain warrants. An outpost's self-authored state has no off-site copy by design (ADR-0031 + no upward push, B7), so *an outpost's own Postgres replication is its entire DR story* — the runbook says this in bold rather than letting "the commander has a copy" be assumed.
- **Retrans instance** — the same pattern plus byte-channel durability: multi-cluster retrans requires **either** S3-compatible delivery targets (already built in the delivery path; a self-hosted MinIO in the enclave keeps this air-gap-legal and principle-4-legal — S3 is never *required*, replicated volumes are the alternative) **or** an operator-replicated RWX volume; the chart gains volume vocabulary either way (C4). One retrans instance = one Postgres — the lease fencing that prevents double-relay is scoped to one database, so a "standby retrans" with its own database is exactly the rejected second-instance pattern (§10).

## 7. The work

### 7.1 Single-region hardening (M26.1 — held for the milestone per D4, settled; every item is a today-bug)

1. **SSE fan-out over the Postgres bus.** The relay `NOTIFY`s a channel on publish; every **api** process holds one reconnecting LISTEN connection feeding its local `sseHub`. Two review-found details are part of the spec, not afterthoughts: **(privilege)** the outbox is FORCE-RLS with cross-org reads reserved to the `scp_relay` role, so the NOTIFY payload carries the full `RelayedEvent` envelope when it fits the ~8000-byte NOTIFY cap, and the api-side reader falls back to fetching oversized rows under the same narrowly-scoped `SET LOCAL ROLE scp_relay` escalation the relay itself uses ([outbox-relay.ts:113](../../apps/server/src/events/outbox-relay.ts)) — extending that reviewed escalation to api pods is named here deliberately; **(delivery)** the bridge is best-effort by ADR-0025's own contract (no replay), so on every LISTEN (re)establishment the api process signals its connected SSE clients to resync, and the web client gains the missing leg review found in [use-event-stream.ts](../../apps/web/src/lib/use-event-stream.ts): invalidate the query cache on every successful (re)connection — today ADR-0025's stated "re-syncs through the query cache" happens on no code path. ADR-0025 gains a multi-process-delivery amendment. When NATS is enabled, the existing `nats-fanout` can carry the same bridge.
2. **A2 — absorbed into M25** (see §4): the campaigns session is porting the change-coordination advisory lock with the N-concurrent race test. M26.1's remaining obligation is verification only — assert the lock and its race test exist (delete-the-wiring style), re-fixing nothing.
3. **Watchdog claims** (A3) — correctly scoped per review: this is a *transaction restructure*, not a reorder. `runWatchdogSweep` today receives one open tx for the entire per-org sweep; the fix mirrors reconcile's pattern — each flagged row claims (SKIP LOCKED or the advisory-lock helper), decides, and **commits in its own short transaction**, with notification dispatch after that commit and the UPDATE's affected-row count actually consulted.
4. **`singletonKey` on the initial sends** (A4): uniform for six loops; federation-sync's forced startup pull gets a distinct `startup` key so the M14.4 wake-swallowing bug is not reintroduced.
5. **Reconnecting LISTEN client** with backoff, shared by the relay wake (A5) and the new SSE bridge.
6. **Pool timeouts as a census** (A6): `connectionTimeoutMillis` + keepalive via one factory that *all four* `new pg.Pool` sites go through — the same inline-pool duplication was already found and fixed once before ([operator-db.ts:6](../../apps/server/src/routes/operator-db.ts) records it).

Each lands with the multi-replica test whose absence let it ship.

### 7.2 Divergence rails (the B1/B2 answer)

Preconditions stated up front, because review proved the v0.1 rails were inert exactly where B1 bites hardest: rails 2 and 3 require the receiver to hold a **real anchor** (`lastAppliedRowHash IS NOT NULL`), which only full-scope peers do — the sparse path deliberately stores `null`. Rail 4 exists to cover everyone else.

1. **Export-side tail check** — a pull whose `sinceSequence` is **at or beyond** the exporter's own journal tail *while the tail's content differs from what the peer recorded* is proof of a fork or rollback. The strict `>` half needs no new wire data (a cursor can never legitimately outrun the origin's tail); the `==` boundary case is owned by rail 2's hash comparison. Refusal: HTTP 409 with a new problem `type: journal_divergence`, distinct from both tampering and scope-asymmetry wording. Wire honesty (review): this is **no request-shape change but an additive response-map change** — `POST /api/v1/federation/exports` (`ExportJournalRequestSchema`) today declares 400/401/403/404; it gains 409, additive under oasdiff. Both sides' Decisions go through `insertDecisionIfChanged` keyed on (peer, divergence reason) — the puller already has that persist-on-change seam ([federation-sync.ts:377](../../apps/server/src/federation/federation-sync.ts), built after a 1,440-identical-Decisions-per-day incident); **the exporter has none today and needs one** — and note the amplification pressure: a refused pull snaps the peer to the frequent (60s) cadence, so without persist-on-change this rail would mint ~1,440 Decision+audit pairs per peer-day until an operator responds.
2. **Anchor verification on pull** — additive optional request field: the pull carries the cursor's `lastAppliedRowHash` alongside `sinceSequence`; the exporter compares it against its own journal row at that sequence and refuses (`journal_divergence`, naming lost-tail restore as the likely cause) on mismatch. Full-scope receivers only (they alone hold real anchors).
3. **Import-side overlap check** — covers the air-gap file path with no wire change, full-scope receivers only: when a bundle's range spans the local cursor, the entry at `cursor.sequence` must match the recorded `lastAppliedRowHash`; a scope-sparse bundle may legitimately omit that entry (review), in which case this rail **does not fire** — absence is not divergence.
4. **Exporter tail attestation** — the scope-independent rail: every export response additionally carries the exporter's own `(tailSequence, tailRowHash)` for the org's journal, signed; the importer persists it as a **monotonic high-water mark per (peer, origin)** and refuses on any regression or content change at the same height. This is what makes B1 detectable for narrow-scope peers, where phases one *and* two are otherwise silent. Wire honesty (review + DESIGN.md §13's own constraint): the *bundle header* cannot gain a key additively — an un-upgraded importer strips unknown keys and then fails every checksum — so on the HTTPS path the attestation rides as a **sibling response field outside the signed bundle** (additive; old SDKs ignore it), and on the file path it needs either a `formatVersion` 2 negotiation or acceptance that strict parsers on old importers reject new-format files **fail-closed** (never silently). The proposal recommends the sibling-field-now, formatVersion-2-later sequencing.
5. **Close the adoption door**: `permitCursorReanchor` — the mechanism the current no-anchor error message *prescribes* — must be refused while a `journal_divergence` verdict is standing for that (peer, origin). Without this, the rails can be undone by following the printed remedy (review's sharpest finding).
6. **Recovery is a designed operation, not "idempotent by construction"** — v0.1's claim was wrong twice (review): `advanceCursor` deliberately never regresses, so no reset-to-genesis path exists; and re-applied re-minted entries would silently no-op against the graph's revision staleness guard (`revision <= existing` returns the row unchanged, [objects-repo.ts:865](../../apps/server/src/graph/objects-repo.ts)) — a "converged" resync that converges nothing. `scp federation resync --peer X` is therefore **net-new, security-sensitive, one-shot, permit-style work at every layer (API → SDK → CLI, principle 3)**: mutually authorized, it resets the importing side's cursor *and* imports in a forced-overwrite mode that bypasses the revision staleness guard **only** under that permit, Decision-recorded on both sides. The runbook states plainly what RPO>0 means: the lost tail's content is *gone*; resync converges everyone on the restored reality, and the divergence Decisions are the permanent record (principle 6). A per-org **generation stamp**, bumped by this operation and by the promotion runbook, is recorded with the Decision so a later forensic reading can attribute which entries pre- and post-date the event (this also gives §5-I1's fencing-failure case a post-hoc identifier; it deliberately does *not* enter the signed entry format in this proposal).
7. **B2's witness — built here, not deferred to an unbuilt mechanism** (v0.1's blocker): importers stop discarding `audit_segment` journal entries and persist `(peer, sequence, contentHash)` — turning **every peer into a passive witness of the exporter's audit-chain head** at near-zero cost, since the entries already flow. The post-failover runbook compares the restored local head against the peers' witnessed heads; `scp audit verify` alone remains structurally unable to see truncation (any prefix verifies) and the runbook says so explicitly. This absorbs the spirit of ADR-0024 O4 for the cross-domain case; O4's filesystem anchoring remains ADR-0024's own deliverable.

### 7.3 Boot-time and doctor checks

- **Decrypt canary, specified against RLS** (v0.1's version could never run — `secrets` is FORCE-RLS and an unscoped read returns zero rows *vacuously*): enumerate orgs, and for each org holding any `secrets` row, attempt one decrypt inside `withTenantTx`; refuse to serve on the first AEAD failure. A zero-row read is never evidence of an empty vault. Gate test: seed a secret, boot with a wrong `SCP_SECRETS_MASTER_KEY`, assert the process refuses — a canary written against the unscoped read passes that test's negation.
- **Production mode refuses ephemeral secrets** (D6) — with the review-found precondition made explicit: **no environment-mode flag exists in config today**, so D6 first introduces one (name, values, default, how compose-eval vs Helm set it) as part of the same decision.
- `scp doctor` gains: DSN fast-fail reachability, `pg_is_in_recovery()` visibility, mTLS file/Secret presence + SAN coverage of every dial URL, `SCP_DELIVERY_S3_ENDPOINTS` consistency, and `scp federation doctor` running §7.2's rails proactively against every peer.

### 7.4 Chart & packaging

- PDB templates + default topologySpreadConstraints (C1).
- **Multi-cluster values contract**, documented as a first-class recipe: one release per member cluster; `postgres.host` the operator's failover-stable endpoint; **`appSecrets.existingSecret` AND `postgres.existingSecret` required and identical everywhere** (chart-generated credentials are single-cluster-only — B9); mTLS Secrets replicated with SANs covering every dial name; NetworkPolicy egress opened to the cross-cluster Postgres endpoint. **Exactly one member cluster runs the migrations Job** (`migrations.enabled: false` elsewhere) — the Job also re-provisions shared role passwords, so this is a correctness rule, not tidiness; role provisioning additionally becomes compare-and-skip-or-refuse rather than unconditional reset.
- **DSN contract per D5**: the single stable endpoint *is* the contract; the URL-derivation code and the `wait-for-postgres` init container stay single-host and the docs say so. (If multi-host is ever taken up it is client-side host iteration with read-write probing or a fronting proxy — a scoped project, not a parsing fix.)
- **Version skew across member clusters** — review caught this contradicting DESIGN §17's "single image version (no skew)" row, which was written for one cluster: the supported window is **N and N+1 only**, and a migration's *contract* half must not ship until every member cluster runs the release that shipped its *expand* half. Mechanism, not prose: each release records a per-member-cluster version heartbeat row; the migrations Job refuses a contract migration while any live heartbeat trails it. DESIGN §17's Upgradeability row is amended alongside the Availability row.
- Retrans volume vocabulary + S3-first delivery guidance (C4) — plus the §9.4 rail: the chart refuses to render a multi-member retrans release with filesystem drop dirs and no shared volume, and the auto-relay tick verifies a built artifact is still readable before treating its ledger row as terminal, reopening it when it is not.
- **Object storage**: build the S3 provider (server code + chart env + credential wiring — today it is a values stub, C3) *or* restrict multi-cluster object storage to replicated RWX; D7 picks.
- **Backup/PITR/restore runbook** (subsumes ADR-0024 F9, landing at `docs/runbooks/` as F9 specified): WAL archiving + PITR as the baseline for every production instance, air-gap-compatible tooling only, an RPO/RTO worksheet per role — **and a section review demanded: "a restore re-executes."** pg-boss state rolling back in lockstep means queued work re-runs, and executor idempotency keys are app-generated per compile (`idempotencyKey = waveTargetId`, a fresh UUID on recompile — [reconcile.ts:1771](../../apps/server/src/coordination/reconcile.ts)), so a restore can re-trigger external side effects with *new* keys. The procedure: quiesce workers (`SCP_ROLE=api` only), reconcile executor/PR state against the restored SCP state, then re-enable; separately, consider deriving executor idempotency keys deterministically so they are restore-stable.
- Ansible: gains a worked multi-cluster inventory example; remains a fleet-of-instances tool otherwise.

### 7.5 Verification (permanent CI, offline)

## 9. Failure walkthroughs (how the design answers the ask)

1. **A member cluster without the primary dies.** LB/GSLB drains it. Other member clusters' api/worker continue against the unchanged primary. SSE clients reconnect onto surviving api pods; per ADR-0025 there is **no replay** — live events during the reconnect window are dropped by design and the client re-syncs through cache invalidation on reconnect (§7.1.1). No persisted data loss. SCP action: none.
2. **The cluster holding the Postgres primary dies.** The operator's HA layer promotes and fences (I1). Surviving compute fast-fails onto the promoted primary (A6 fix). Sync-quorum: RPO=0, done. Async: the rails (§7.2) turn any lost tail into named `journal_divergence` refusals + Decisions on the next pulls; the resync operation converges the fleet; the audit trail records the event. Recovery time is bounded and computable: worst-case outpost staleness ≈ effective pull cadence (60s frequent / up to 900s sparse, 12h ceiling for poke-mode peers) + K × per-URL dial timeout + DNS TTL — the runbook's worksheet does this arithmetic per peer, and D3 notes that a poke-mode peer's failover recovery is bounded by its *sparse* interval, a deliberate cost of poke mode.
3. **An outpost's cluster dies.** Same pattern one tier down. The commander's view degrades honestly (freshness anchored to confirmed transfers reports staleness/unknown, never fabricated liveness). Self-authored outpost state survives exactly as far as the outpost's own replication (B7, stated in bold in the runbook).
4. **A retrans cluster dies.** Two cases (review): a crash **before** the ledger commit leaves the row `pending` — the lease lapses and the next tick rebuilds from scratch (already built, §3). A crash — or cluster loss — **after** commit strands a `submitted` artifact on whatever storage held it: with S3 delivery targets it survives; with pod-local filesystem drops it is gone *and the loop will not retry* (the row is no longer `pending`; reopen is a manual operator action today). Hence §7.4's rail: readable-artifact verification before a build is treated as terminal, and the chart refusal of un-shared filesystem drops for multi-member retrans.

## 10. Explicitly out of scope / rejected

- **Active-active multi-primary commander.** Single-writer authority ("no merge algorithm exists because none is needed") is the platform's core simplification; a multi-primary commander re-imports the entire conflict problem to shave failover minutes. Rejected.
- **A standby *instance* as DR** (second commander with its own database, identities, journals). It would fork every org's journal by construction — it is the B1 hazard turned into an architecture. Multi-cluster means member clusters of one instance, never a shadow instance.
- **SCP shipping/managing Postgres HA.** Execution creep against principle 1, a required-dependency question under principle 4, and §16 already settled external-by-default. SCP states requirements; the operator provides the database.
- **SCP orchestrating its own failover** (health-checking itself, flipping DNS, promoting replicas). Coordination-not-execution applies to SCP itself; the long-term home for "SCP managing SCP" is the charter's campaigns vision, not a hidden control loop.
- **A second consensus/coordination store** for leader election. Nothing in §7 needs one; charter principle 4 bars it without owner sign-off, and none is requested.
- **Federation as backup.** Journals are scope-filtered at export, domain-local objects never federate (ADR-0031), and peer copies are read-only replicas of a subset. Restoring an instance from its peers is structurally impossible and must never be assumed; backups (§7.4) are the answer. (The §7.2.7 witness makes peers *detectors* of truncation — never *sources* of restoration.)
- **Named residual risk — unfenced split-brain.** If the operator's HA layer fails to fence, SCP silently loses the demoted side's writes (I1). The §7.2.6 generation stamp makes the event forensically attributable after the fact; nothing in this proposal makes it impossible, and the runbook says so.
- **M16.4 upward push / return-path confirmation** — adjacent (it would shrink B7's blast radius) but independently scoped; tracked where it already lives.
- **Entry-format changes** (epoch in the signed journal-entry format, richer conflict semantics) — the reserved `base_revision`/`conflict` fields stay reserved; §7.2's rails deliberately live in request/response/sibling-field space and local persistence, not the signed entry format.
