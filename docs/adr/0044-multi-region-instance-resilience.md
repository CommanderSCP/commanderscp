## Context

The owner asked, verbatim in substance, for a commander and outpost to survive a regional or cluster outage, and for the ability to span multiple regions and clusters. Grounding work measured the existing architecture against that ask and found it closer than expected — correctness already concentrates entirely in Postgres, with N competing, crash-resumable workers (DESIGN.md §8) — but found no statement anywhere of how an instance survives losing the cluster it runs in. DESIGN.md §17's Availability row read, in full, "HA via the org's standard Postgres HA"; no milestone touched DR; no backup/PITR/restore tooling existed (a gap [ADR-0024](0024-decision-and-audit-retention.md) F9 had already named and never built).

A five-lens adversarial review (two fact-verification passes, self-contradiction, design red-team, fix feasibility) measured three classes of gap, detailed in the proposal §4:

- **Class A — broken today, single region, default chart.** SSE live delivery is structurally broken across api/worker process boundaries (A1); campaign reconciliation has no advisory lock around its plan-compile-persist sequence (A2, absorbed into M25); the watchdog sweep has no per-row claim inside one long transaction (A3); self-rescheduling loops omit `singletonKey` on their initial send (A4); the outbox relay's LISTEN connection never reconnects (A5); connection pools have no timeout/keepalive across four call sites (A6).
- **Class B — failover-semantics hazards, dormant until the first real failover.** Lost-tail journal divergence is fail-silent for a lagging async restore and mis-prescribed once detected (B1); the local audit chain forks the same way with no detector (B2); the secrets-vault KEK, the cookie secret, and mTLS material are cluster-local k8s Secrets that do not replicate with Postgres (B3–B5); peer addressing is exactly one URL with no dial timeout (B6); an outpost's self-authored tail has no off-site copy (B7); clock authority is mixed between database and app-process time (B8); database role credentials are per-cluster-generated and the migrations Job unconditionally resets them, so a second member cluster naively installed clobbers the first's credentials on the shared database (B9).
- **Class C — deployment/packaging gaps.** No PodDisruptionBudget or anti-affinity templates (C1); single-host DSN parsing throughout (C2); object storage and the scan-db cache are single-node RWO PVCs, and the `objectStorage.s3.*` values block is an unwired stub (C3); retrans drop directories have no chart volume vocabulary (C4); the migrations Job has no cross-release mutex and re-provisions shared role passwords (C5, the mechanism behind B9); no backup/PITR/restore guidance exists anywhere (C6, absorbing ADR-0024 F9).

This ADR records the accepted design that answers the ask and closes these gaps, and the seven owner decisions that settled its open questions. It documents an accepted design; it does not re-open any of them.

## Decision

### The member-cluster model

**Multi-cluster is a property of an instance, not a multiplication of instances.** An **instance** is one running deployment of the SCP platform around **one PostgreSQL database**; it is multi-tenant, and federation identity, journal, cursor set, peer set and role are all per-org. A **member cluster** is one Kubernetes cluster (or compose/VM site) running some of an instance's api/worker compute; an instance spans one or more member clusters, and every one of them reads and writes the same primary. An instance spanning three member clusters in two infrastructure regions is still one database and one per-org journal set. The rejected alternative — a second "standby" instance with its own database — is recorded below. `docs/GLOSSARY.md` gains the **member cluster** and **XO** entries and amends **instance** accordingly (D1).

A consequence of multi-tenancy worth stating plainly: a multi-tenant commander's failover moves the dial address for *every* tenant org's peers at once, and mixing commander-role and outpost-role tenants on one database couples their DR postures (D2).

### I1 — One writable primary, guaranteed below us, and the consequence stated

At any moment exactly one Postgres primary accepts writes for an instance. SCP does not build or ship this guarantee — it is the operator's Postgres HA layer (streaming replication + Patroni, CloudNativePG, a cloud-managed service; all fine, all air-gap-compatible in self-hosted form). SCP states the requirement precisely in the operations runbook, including its teeth: **if fencing fails and a demoted primary keeps taking writes, SCP detects nothing and silently loses those writes** — every serialization primitive SCP uses (advisory locks, sequence uniqueness) is per-database and is satisfied independently, and identically, by both sides of a split brain. That residual risk is either accepted in writing or narrowed by the promotion runbook's generation stamp (see the divergence-rails subsection below). SCP adds **no second consensus store** — charter principle 4 needs no new required stateful dependency, and this design needs none.

### I2 — Compute is symmetric and stateless across member clusters, and all of it reads the primary

One Helm release per member cluster, all pointed at the same logical DSN, all sharing the same `appSecrets`, `postgres.existingSecret`, and mTLS material. There is deliberately **no read-replica offloading of correctness reads anywhere in this design**: read-time admission predicates — policy gates, freeze holds (including M25's per-target freeze admission, re-evaluated every tick) — are correctness reads, and an instance that offloaded them to a replica would evaluate a freeze against lagged state and silently ship into it. Every worker therefore reads and writes the one primary. Once Class A is fixed, the competing-consumer design makes any worker anywhere correct; a distant member cluster degrades tick latency and staleness, never correctness. Guidance, not machinery: run the bulk of worker capacity near the primary; a distant member cluster is a survival organ, not a latency optimization.

### I3 — One dial address per instance, with a fallback list

The primary answer to "outposts must reach whichever cluster is alive" is operator DNS/VIP/GSLB on the commander's base URL — zero schema change. Because air-gapped and enclave networks routinely lack failover DNS, the peer row additionally grows an **ordered list of dial URLs** (D3): tried in order per pull attempt, each attempt under an explicit per-URL timeout. The list refuses scheme downgrades at write time (an `https` base with an `http` fallback is a 400, never a silent bearer-only dial), and the commander's federation server certificate must carry every dial name — VIP, GSLB name, each fallback host — as a SAN (a runbook precondition). The list is provisioned per outpost through the same door as the existing peer-row PATCH (ADR-0022: peer rows are local, per-side, never journaled); its value is that it is provisioned **before** the failover instead of during it. Entries are labeled, and the standby member cluster's entry carries the **XO** designation, so the fallback is self-describing at every outpost, and `scp federation doctor` can check that an XO entry exists and answers.

### I4 — RPO > 0 must be loud

Synchronous-quorum replication (RPO=0) is the supported posture for a commander-hosting instance (D2) and the only posture in which lost-tail divergence cannot occur. Async replication is a legitimate operator choice for outposts and retrans, so the platform converts "lost tail" from silent divergence into a named, fail-closed, Decision-recorded event — the divergence rails, below. **D2's owner condition is restated here because it is an invariant, not a preference:** this posture governs *database replication only*. It neither enforces poke mode nor alters federation transport in any way. Outposts and retrans work in isolation, and when connected (non-air-gapped) they regularly poll the commander on their own cadence; poke stays strictly opt-in ([ADR-0009](0009-optional-poke-mode-federation.md)).

### Role-specific needs beyond the common pattern

- **Commander-hosting instance** — the full pattern; sync-quorum recommended (D2); divergence rails mandatory. The posture is per *instance*, so it is set by the strictest role any tenant holds.
- **Outpost-hosting instance** — the same pattern at whatever tier the domain warrants. An outpost's self-authored state has no off-site copy by design ([ADR-0031](0031-domain-local-objects-never-federate.md) plus no upward push, B7), so an outpost's own Postgres replication is its entire DR story — the runbook states this in bold rather than letting "the commander has a copy" be assumed.
- **Retrans instance** — the same pattern plus byte-channel durability: multi-cluster retrans requires either S3-compatible delivery targets (already built in the delivery path; a self-hosted MinIO keeps this air-gap-legal and principle-4-legal, since S3 is never *required*) or an operator-replicated RWX volume. One retrans instance is one Postgres — the lease fencing that prevents double-relay is scoped to one database, so a "standby retrans" with its own database is exactly the rejected second-instance pattern.

### The divergence rails — where they live, and where they deliberately do not

The rails that turn a lost async tail into a named `journal_divergence` refusal (export-side tail check, anchor verification on pull, import-side overlap check, exporter tail attestation, closing the `permitCursorReanchor` adoption door, and the local audit-chain witness) are specified in full in the proposal §7.2. What this ADR fixes as a durable architectural fact, so it is never rediscovered as an open question: **these rails live in request/response space, an additive sibling response field, and local persistence — never in the signed journal-entry format.** The reserved `base_revision`/`conflict` fields on the entry stay reserved and untouched. A per-org generation stamp, bumped by the resync operation and by the promotion runbook, is recorded with the Decision so a later forensic reading can attribute which entries pre- and post-date a failover — and it too does not enter the signed entry format. This boundary is deliberate (see Alternatives rejected) and is what keeps the rails additive and safe for an un-upgraded peer to ignore.

### D1 — Vocabulary: "member cluster" and qualified "infrastructure region" enter the glossary; "instance" is amended

**Settled: A.** "member cluster" and qualified "infrastructure region" enter `docs/GLOSSARY.md` as new entries, and the existing `instance` entry is amended to say its compute may span member clusters while its one Postgres stays load-bearing. Geography is never named with bare "region" when the subject is SCP's own placement — that word stays spent on the tenant's deployment-target locality; "infrastructure region" is qualified for exactly this reason, the same reasoning that keeps "cross-domain promotion" always written in full.

### D2 — Sync-quorum for commander-hosting instances, with a condition

**Settled: A, with a condition.** Sync-quorum (RPO=0) is the supported posture for any commander-hosting instance; async-with-rails is acceptable for outpost/retrans instances; the strictest tenant role governs a mixed instance, and the runbook warns about role-mixing. **The owner's condition, verbatim in substance: this must not enforce poke mode on outposts or retrans.** The posture is database-replication-only — outposts and retrans work in isolation and, when connected (non-air-gapped), regularly poll the commander; poke remains opt-in ([ADR-0009](0009-optional-poke-mode-federation.md)). This condition is restated as part of invariant I4 above, not merely noted once and left to erode.

### D3 — The ordered dial-URL list, and the XO designation

**Settled: B, plus the XO designation.** The ordered dial-URL list is built with write-time scheme-downgrade refusal, SAN coverage, and a per-URL timeout, with labeled entries. **"XO" enters the vocabulary** as the designation for the standby member cluster: sync standby, warm compute, and the pre-provisioned fallback dial entry, with doctor-reported readiness and a "the XO takes command" runbook procedure. The owner explicitly considered and rejected reading the XO as a second commander instance — that reading was rejected for the same two reasons a standby *instance* is rejected below (journal fork by construction, dual signing identity): the XO is a member-cluster designation, the same command structure with a designated successor, never a second captain.

### D4 — The M26.1 hardening set is held for the milestone

**Settled: B — held for the milestone.** The single-region hardening set (Class A, proposal §7.1) lands as M26.1, the first increment after this proposal's acceptance, not ahead of it. Recorded consequence, stated without hedging: A1's SSE break and B9's credential-clobber exposure remain live on the default chart until M26.1 ships.

### D5 — One stable DSN endpoint is the contract; multi-host DSN support is out of scope

**Settled: A.** One stable, operator-provided endpoint is the DSN contract. The URL-derivation code and the `wait-for-postgres` init container stay single-host, and the docs say so. Multi-host DSN support — client-side host iteration with read-write probing, or a fronting proxy — is out of scope for this proposal; if ever taken up, it is a scoped project, not a parsing fix.

### D6 — A production/evaluation deployment-mode flag, and a production refusal of ephemeral secrets

**Settled: A, both halves.** A deployment-mode config surface is introduced (production vs. evaluation; Helm defaults to production, compose-eval and dev set evaluation), and a production boot refuses ephemeral, randomly generated `SCP_SECRETS_MASTER_KEY`/`SCP_COOKIE_SECRET`. No environment-mode flag exists in config prior to this decision; D6 introduces one as part of the same decision, not as a separate follow-on.

### D7 — The resilience runbook and the S3 object-storage provider are M26 scope

**Settled: M26**, both sub-parts confirmed. The runbook lands at `docs/runbooks/resilience.md`, subsuming [ADR-0024](0024-decision-and-audit-retention.md) F9's never-built backup/growth/sizing runbook. The S3 object-storage provider gets built (closing C3's unwired values stub) — the alternative, restricting multi-cluster object storage to replicated RWX only, was not taken.

## Consequences

- `docs/GLOSSARY.md` gains **member cluster**, **XO**, and **infrastructure region** entries and amends **instance**; the existing `region` entry is untouched and cross-referenced from the new entries.
- `docs/DESIGN.md` §17's Availability and Upgradeability rows are rewritten to point at `docs/runbooks/resilience.md` (once built, per D7) and this ADR. The Upgradeability row's prior "single image version for api+worker (no skew)" is superseded: **across member clusters of one instance, the supported version-skew window is N and N+1 only**, and a migration's contract half must not ship until every member cluster runs the release that shipped its expand half. This is a mechanism, not prose — a per-member-cluster version-heartbeat row, and the migrations Job refuses a contract migration while any live heartbeat trails it.
- The default chart remains single-cluster-shaped until M26.3 ships the multi-cluster values contract (`appSecrets.existingSecret` and `postgres.existingSecret` required and identical everywhere, exactly one member cluster running the migrations Job, PDB/spread templates); nothing in this ADR changes chart behavior by itself.
- No new required stateful dependency is introduced anywhere in this design (charter principle 4 stays satisfied); no second consensus store, no mandatory broker.
- Recovery time after a primary-cluster loss becomes bounded and computable (sync-quorum: RPO=0, done; async: rails convert lost tail into a Decision-recorded resync), and the runbook carries the per-peer arithmetic (dial-timeout budget, pull cadence, DNS TTL).
- The signed journal-entry format is unchanged by this ADR and by the divergence rails it accepts; any future entry-format change (an epoch field, richer conflict semantics) is a separate, not-yet-proposed decision.

## Alternatives rejected

- **Active-active multi-primary commander.** Single-writer authority — "no merge algorithm exists because none is needed" — is the platform's core simplification; a multi-primary commander re-imports the entire conflict problem to shave failover minutes. Rejected.
- **A standby *instance* as DR** (a second commander with its own database, identities, and journals). It would fork every org's journal by construction, and it would fork per-org signing identity too — the Ed25519 federation keys and cosign keys that ride the database (`instance_keys`, `instance_cosign_keys`) would exist twice, unsynchronized. It is the lost-tail hazard turned into an architecture. Multi-cluster means member clusters of one instance, never a shadow instance. This is also why the **XO** is defined as a member-cluster *designation* (D3) — the same command structure with a designated successor, never a second captain.
- **SCP shipping or managing Postgres HA.** Execution creep against charter principle 1, a required-dependency question under principle 4, and DESIGN.md §16 already settled external-by-default for Postgres. SCP states the requirement precisely; the operator provides the database.
- **SCP orchestrating its own failover** (health-checking itself, flipping DNS, promoting replicas). Coordination-not-execution applies to SCP itself; the long-term home for "SCP managing SCP" is the charter's campaigns vision, not a hidden control loop inside this proposal.
- **A second consensus/coordination store** for leader election. Nothing in the design needs one; charter principle 4 bars a new required stateful dependency without owner sign-off, and none is requested here.
- **Federation as backup.** Journals are scope-filtered at export, domain-local objects never federate ([ADR-0031](0031-domain-local-objects-never-federate.md)), and peer copies are read-only replicas of a subset. Restoring an instance from its peers is structurally impossible and must never be assumed; backups are the answer. The audit-chain witness (peers passively recording the exporter's audit-chain head) makes peers *detectors* of truncation — never *sources* of restoration.
- **Entry-format changes** (an epoch field in the signed journal-entry format, richer conflict semantics). The reserved `base_revision`/`conflict` fields stay reserved and untouched. The divergence rails deliberately live in request/response/sibling-field space and local persistence — never the signed entry format — so an un-upgraded peer can ignore what it doesn't understand instead of failing a checksum it was never told to expect.
- **Named residual risk, accepted rather than engineered away — unfenced split-brain.** If the operator's HA layer fails to fence a demoted primary, SCP silently loses the demoted side's writes (I1) — no serialization primitive SCP holds can see across two independently-satisfied databases. The generation stamp (see the divergence-rails subsection) makes the event forensically attributable after the fact; nothing in this design makes it impossible, and the runbook says so plainly rather than implying a guarantee that does not exist.
