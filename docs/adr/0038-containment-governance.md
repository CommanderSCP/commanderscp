## Context

#249 shipped **detection**: a `governance.reach.changed` Decision whenever a containment write changes which policies reach an object. #244 shipped **custody**: a move needs `object:write` at source and destination. Neither prevented a trusted-at-both-ends actor from moving an object out from under a policy, and the proposal's §4 asked the owner whether to prevent it at all, and how. Separately, deleting a container tombstoned it and left everything beneath it live — a service's components orphaned, a component's placements dangling (placements are pair-derived rows, not edges the cascade sees) — because every containment route joins `parent.deleted_at IS NULL` on purpose.

Grounded facts that decided the shape (all measured, file:line in proposal §9.1): every writer role (Operator, Approver, Administrator, Owner) holds `object:write` and **there are no custom roles and no route that authors one**; IaC apply authorizes at apply time with the *real* applying principal through a drained check list, so a door-only check ships inert on IaC unless the apply twin carries it too; `deleteObject` already counted three dependent routes (`domain_id` children, `contains` children, placements) and used the count only to decide whether to record a Decision.

## Decision

1. **`governance:move` is a permission, and its enforcement is a top-down monotone lattice of *rungs*.** A rung is the instance or one container object (org root, containment domain, service, assembly). Enforcement applies to a move iff the **instance rung is enabled** or **any object on the moved object's containment chain or on the destination's chain carries an enabled rung** — a monotone OR: *"flipped on/off at the commander level; if enabled there, orgs can't disable it; if an org enables it, a service can't disable it"* (owner). The instance rung **activates** (it does not merely permit — the owner's words over the M21 unlock analogy). Disabling a rung beneath an enabled one is refused 409 naming the upper rung, so a "successful" disable never leaves enforcement silently on. There is **no computed trigger**: whether a move needs the permission depends only on which rungs are set, never on which policies happen to match — the reason §4(a) was rejected stays respected.
2. **When enforcement applies, the actor must hold `governance:move` at-or-above the moved object AND at-or-above the destination — with no org-root exemption.** #244's two org-root exemptions rest on custody ("the org root cannot gain or lose custody"); governance is different: leaving a governed subtree for the org root is exactly the reach reduction this permission gates. The absence of the exemption is written beside the two existing ones in `containment-parent-authz.ts` and cross-referenced from `governance/move-enforcement.ts`.
3. **`governance:move` is held by Administrator and Owner by default** (the roles that already hold `policy:write`). Granting it to Operator-and-above would have made the switch inert until custom roles exist. Enabling a rung therefore means "moves under here are an Administrator act"; everywhere no rung is set, daily Operator reorganisation is unchanged.
4. **The check lives at every door that moves an object**, including the ones a census found after the first build: the containment-parent door (`domainId` writes on existing rows), the IaC apply twin (**both** the `domainId` diff and the `contains` relationship diff), `PUT /components/{id}/service`, `/relationships` `contains` POST/DELETE, and `POST /discovery/accept` minting a `contains` edge onto pre-existing objects. A child *created* in the same discovery batch is exempt (a create is not a move — the same line #244 draws). Federation import, overlay and hand-fill are carved out with the reason stated in code (synthetic or drained subjects; the receiver does not referee). Detection (#249) is untouched.
5. **Deleting a container that still has containment children is refused, before the tombstone, on all three dependent routes** — `domain_id` children, `contains` children, and placements naming the row — with the blockers named (type, urn, and the remedy route). Carve-outs mirror the edge cascade exactly: `federationImport` (a peer's tombstone arrives by journal and is applied) and `removedForeignShadow` (local cleanup of a foreign shadow row). This retires the deliberate route-2 asymmetry the domain-delete guard's control test used to protect, and closes the dangling-placement gap by refusal rather than by cascade.
6. **Door-level authorization refusals are sentence-only — no `decision_id`.** Every door throws from inside the caller's tenant transaction, so a Decision written there is rolled back with the refusal and its id would name a row that does not exist. The sentence carries the whole explanation (which rung, which tier and name, which end the actor lacks the permission at); the audit log carries the refused write. This is consistent with every other permission 403 in the system (`object:write`, `policy:write`, #244's own move refusals). Charter principle 6's `decision_id` is for **engine verdicts** — gates and policies — which a permission refusal is not. The alternative (persist out-of-band before throwing, `federation/promotion-repo.ts` shape) was offered and declined.

## Storage and surface

Migration `0079`: `governance_move_rungs` (org-scoped RLS; `subject_object_id` PK, the tier **literal** stored at write time, who enabled it, when, the Decision) and `governance_move_instance_rung` (a singleton in exactly the `dependency_subscription_unlock` shape — tenant `SELECT`-only, `FORCE ROW LEVEL SECURITY`, no write policy; written only through the operator-token `PUT` on a raw admin pool). One resolver, `governance/move-enforcement.ts`, walking `containmentChain` (loud, ADR-0037). API: the explain read `GET /objects/{type}/{idOrUrn}/governance-move-enforcement`; `GET/PUT/DELETE /governance/move-enforcement/rungs[/{idOrUrn}]` (`policy:write` at-or-above the subject; every write records a Decision and an audit event in the same transaction); `GET/PUT /instance/governance-move-enforcement` (operator token). SDK `client.governanceMove.*`; CLI `scp governance move-enforcement …`; **Admin › Governance** on both the commander and the outpost site (an outpost's local moves are real moves; the instance rung is read-only there with a CLI pointer). IaC rungs and per-object "governed here" lines are follow-ups.

## Consequences

- Nothing changes until a rung is set: the four suites #244/#249 pinned (`containment-move-authz`, `containment-move-cycle-and-source-authz`, `governance-managed-write-doors`, `subscription-authoring-guard`) are byte-unedited and green.
- #249's route-3 recorder (`recordContainerDeletionReachChange`) now fires only on the two delete carve-outs — clause 5 refuses the case it recorded.
- An org that enables a rung will see Operators' moves under it refused 403 with the rung named; the remedy is in the sentence (an Administrator moves it, or `policy:write` disables the rung — which is itself refused if an upper rung holds).
- Verified by mutation at every door (each check deleted alone → its own case red; the apply twin deleted alone → only the IaC case red), and by two adversarial passes that found the IaC-relationship and discovery-accept doors open and closed them before this ADR was written.
